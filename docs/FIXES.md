# Josi fixes list

Collect fixes here and batch them into updates. Adding an item does not trigger implementation or a rebuild. On October 20, Roman authorized investigation, fixes and one build for items 1 and 2.

1. **Reduce the chat queue polling interval from 30 seconds to 1 second.** Implemented and tested for native.19, now installed. The worker checks the queue every second, never overlaps queue passes, and keeps periodic maintenance on its existing 30-second cadence. This reduces the wait before an idle worker picks up a message; it does not set the model's response time to one second.

2. **Resolve enrollment success followed by an empty device list.** Enrollment confirmation and inventory handling corrected and tested for native.19; Roman confirmed that the device is enrolled after the native.20 update; website automation testing is now in progress. Enrollment now re-reads the committed Vault inventory and the client verifies that the exact Mac is present before reporting success. Devices, Enrolled Mac and protected approval use the same independently refreshed inventory. Failed or malformed reads display an error; stale replies cannot replace a verified enrollment. Saved devices, pending approval requests and desktops have distinct refresh buttons. Tests cover authenticated enrollment/read-back, a separate real PostgreSQL connection, unrelated settings failure, malformed/stale native responses, owner isolation and Vault locking. The original live record was not accessible for inspection, so its specific cause has not been established. No existing enrollment was rewritten or recreated.

   **Native.20 follow-up:** The 3:34–3:35 PM attempts failed administrator verification with HTTP 401; Roman confirmed a wrong enrollment password and corrected it. Subsequent attempts at 3:46 and 3:48 passed verification and the second Touch ID prompt, then cancelled before commit. The native code checked foreground state immediately after the helper returned, racing macOS's restoration of the review window. The client now waits within the existing approval deadline for the review to be visible and Josi active; cancellation, closure and expiry still stop it. The same handoff applies to storage and automation approval. Errors retain their actual enrollment stage and bounded server reason instead of attributing every failure to server-Mac approval. Regression checks pass. Roman subsequently confirmed successful device enrollment on October 20. Website automation acceptance is separate and remains in progress.

3. **Connect Windows antivirus scanning on the Windows development server (next build).** Requested by Roman on October 21. The installed Windows server scans uploads through AMSI (Microsoft Defender or the registered antivirus) with `services/scanner/windows_amsi.py` and a bundled private Python. The development server started by `scripts/windows/dev/Start-DevServer.ps1` sets neither `JOSI_PYTHON_EXE` nor `JOSI_SCANNER_ADAPTER` and has no private Python, so uploads that require a scan are refused. Fix: stage the pinned Python 3.12.15 runtime for the dev server and set both variables. Not started.

4. **Password fields: show-password toggle, confirmation field and live checks (next build).** Requested by Roman on October 21. In the Windows app, the password entry for creating the owner account during setup (and every other place a new password is chosen, such as invitation/password reset) needs: a show/hide password button; a second "Confirm password" field; and visible checks that the two match and that the password is at least 12 characters, with the Create/Save button disabled until both pass. Not started.

5. **Model setup: Choose step is too long and Continue is far down (next build).** Reported by Roman on October 21. Make the step compact (smaller provider rows instead of large cards, other providers behind a "More providers" expander), keep Back/Continue in a footer that is always visible, and let choosing a provider move straight to the next step. Not started.

The Windows app's sign-in page needs a show/hide password button on the password field and a visible "Forgot password?" link that goes straight to requesting a reset (the server's existing `/auth/forgot-password` flow).
