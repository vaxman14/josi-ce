# P4 permission engine and device bridge

Status: in progress. The first checkpoint supplies shared scope contracts and pure permission analysis. It does not expose a dispatch permit, change legacy approvals, enroll a device or enable an automation executor.

## Implemented analysis

`packages/protocol/src/permissions.ts` owns the same effect vocabulary used by Cardinal Rules. Moving that unchanged list to the browser-safe package does not change existing Cardinal semantics. Permission policies bind exactly one user, server, device and isolated workspace. An enabled switch with no grants permits nothing.

Modes are Deny, Ask, Allow for the original task, Allow until an exact UTC timestamp, and Standing permission. Deny beats Ask, which beats Allow, independent of order. Unsupported fields, effects, target types, ambiguous origins, malformed identities and missing limits are rejected rather than repaired. There is no wildcard identity or implicit folder recursion. Rules use exact browser family/profile/origin; file-root identity/revision and path components; installed application identity/revision; network origin and verified locality; runtime/sandbox identity/revision; model configuration identity/revision; or credential item/version plus destination. A credential-use grant is not permission to return its secret to chat or transmit it to a model.

Analysis requires coverage of every effect and concrete target. A generic click, shell command or browser submission with unknown business effects pauses. A model cannot certify effect coverage. File-path comparison is not a handle/symlink containment proof; canonical targets must come from verified adapters. DNS locality, redirects, frames, app identity, data destinations and multi-file effects need equivalent adapter evidence. Grants do not make an unsupported adapter supported. Authority expansion and Vault administration are always denied through automation.

Limits include elapsed time on the original durable task, action count and bytes. Time stops at the boundary; byte and action quotas permit the last in-budget operation. Missing or uncertain counters/byte counts do not become zero. Every overlapping active grant is charged once per proposal, its affected bytes are summed, and all its limits apply. An unlimited overlapping grant cannot bypass a narrower active limit. Expired grants and grants for another task do not apply. Counters must retain reservations and uncertain attempts across retries; edits must not erase prior consumption.

The result is `covered`, `ask`, `deny` or `pause`, always with `executionEnabled: false`. `covered` describes only ordinary permission coverage. Cardinal Rules, current Vault authority, authenticated device-owner consent, observation/focus binding, exclusive control, replay protection and atomic budget reservation remain mandatory at dispatch. Pure tests cannot establish those operational properties.

## Legacy-approval replacement mapping

These are explicit replacement requirements, not implemented exemptions. Every existing route retains its current ask/deny behavior in this checkpoint. Migration must archive previous settings and decisions in the Vault; it must not turn one-time approvals, global automatic preferences or notification-device registration into automation authority.

| Existing operation/gate | Replacement required for autonomous scoped work | Current checkpoint |
|---|---|---|
| PC browser view/fill/submit/download/upload/purchase (`core/pcControl.ts`) | Exact enrolled device/workspace/profile, origin including frames/redirects, verified operation effects, file source/destination where applicable, transaction-specific merchant/currency/amount ceilings for purchases | Pure browser/file scopes tested. Browser adapters, purchase semantics and dispatch remain unavailable; legacy prompts retained. |
| PC app launch/control/close/terminate | Installed app identity/version, observed window/control generation, all effects; termination must separately account for unsaved work | Pure application scope tested. Generic UI effects cannot be asserted complete; no autonomous exemption. |
| PC commands, scripts, software install/remove, settings | Verified isolated runtime/egress/filesystem capabilities, interpreter identity and full resulting effects; unsupported host/system mutations refused | Pure runtime scope tested. No blanket terminal/app grant, executor or install/remove exemption. |
| PC secret access | Vault item/version, exact approved use/destination, no plaintext return, current projection lease and revocation | Destination matching tested. No credential materialization or dispatch exemption. |
| PC security settings/administrator elevation; Cardinal changes; permission expansion | Protected human control, fresh appropriate account verification, exact command and one-use evidence; platform consent separately enforced | Human-only. Cannot become an ordinary standing grant. |
| Local workspace create/edit/mkdir/move/delete (`storage/localWorkspace.ts`) | Current administrator mapping ceilings, exact source and every destination, pinned filesystem handles, preconditions/recovery behavior, current scoped grant and one-use dispatch | Pure file scope/limit analysis tested. Existing exact-operation approval and write lease retained. A read/write grant never implies deletion/export. |
| Storage delete confirmation (M47) and source/cloud mutations | Separate delete capability, owner and mapping limits, exact source/provider/version, trash/recovery semantics and verified completion | Existing confirmation retained. No adapter exemption yet. |
| Email new recipient (M43, `mail/send.ts`) | Exact recipient set, sender/account, thread, newly exposed history and message content; changed history or recipient invalidates the proposal | Not covered by a browser/network grant. Existing exact-message approval retained. |
| Email attachments (M44, `mail/send.ts`) | All recipient/history checks plus exact file identities/content, disclosure scope and size limits; all attachment and recipient effects checked together | Existing attachment-first approval retained; no autonomous exemption. |
| Custom API writes/deletes (`connectors/customApiCalls.ts`) | Existing administrator endpoint allowlist, current connection/schema/credentials, exact request and verified business effects; private-network policy remains | Existing one-use pending-call approval retained. HTTP method alone is insufficient evidence. |
| Workflow execution (`connectors/workflows.ts`) | Current provider/catalog/schema and exact inputs, verified downstream effects, scoped grants, durable reservation and uncertain-result reconciliation | Existing proposal/claim and credential rechecks retained. Workflow names cannot establish effect coverage. |
| General task approvals and user/admin ceilings (`core/approvals.ts`, `core/actionState.ts`) | Verified action-specific replacement above, exact proposal revision, original task and current authority; no widening of administrator ceilings | Existing approval behavior retained. No global bypass switch. |
| Sensitive action step-up (`core/stepUp.ts`) in direct chat and subscription MCP (`agent/assistantAgent.ts`, `agent/mcp/server.ts`) | A shared server/device gate for a supported preauthorized effect, consistently applied before dispatch on every route | Existing step-up retained pending shared gate integration. A second route cannot use pure `covered` as an exemption. |
| Workspace code run (`storage/workspaceCoding.ts`) | Verified sandbox and resource/network/file restrictions, exact runtime identity, scoped execution grant and reservation | Existing human approval retained; general execution scope alone does not prove containment. |

For each row, integration must test both autonomous success inside an exact grant and refusal on altered scope, missing verifier, revoked policy, alternate route and replay. Platform/provider human steps and protected administration stay human-only. The operation matrix must be updated as each live adapter earns its exemption; documentation alone never removes a check.

## Validation and remaining work

19 October 2026: 99 tests passed across permission, Cardinal semantics and protocol suites; protocol/core type build passed. Cases include all four browser families, cross-identity requests, exact-origin/profile changes, file descendants/root revisions, app/runtime/model changes, credential destinations, incomplete alternate-route effects, precedence, original-task expiry/limits, overlapping quotas, unknown counters, overflow and strict parsing. These are deterministic synthetic tests, not live browser/OS enforcement evidence.

Next: canonical Vault policy lifecycle and effective-permission preview; device enrollment and owner consent; authenticated local/remote bridge; protected control verification; durable atomic reservations and dispatch receipts; permission review agent that can only narrow authority; settings UI; local emergency stop and exclusive controller; legacy-route integration and migration. Schedules, recording, transaction budgets and additional business effects remain unsupported until their exact semantics and adapters are implemented. P0/P2 runtime and containment gates remain open.
