# P3 Cardinal Rules implementation evidence

This is an independent foundation checkpoint, not a completed phase or an enabled automation feature. The P2 protected Vault record store is tested; remaining runtime credential and restore gates stay open. No active rule, permission or installed-server setting is changed by this work.

## Implemented semantics

`cardinalRules.ts` supplies a strict versioned schema, exact explanation, restrictive evaluator and side-effect-free simulator. Each rule requires wording, label, exact action selection, explicit user/server/device/workspace/task selectors, a supported restriction and Deny/Pause behavior for missing facts. IDs are exact; names, patterns, implicit defaults, unknown fields and unsupported restrictions are rejected. Wording is annotation for human/model review; it cannot change executable meaning.

The first supported restrictions are action denial and an inclusive maximum original-task duration in integer seconds. Purchase budgets, recipients, folder containment and other business constraints remain unsupported until their adapters can verify those effects. This checkpoint does not convert a generic UI click into a verified business operation.

The evaluator returns `deny`, `pause` or `no_restriction`. The last result is not permission. Explicit denial wins. An incomplete/unknown effect set cannot prove an action is unaffected. Missing scope or clock facts follow the specified deny/pause behavior; unknown operations and invalid rules pause. Protected authority/Vault administration is always refused through this automation evaluator. P4 must supply authenticated identity, complete effect classification, ordinary grants, original-task time and current device/Vault authority. The pure evaluator does not authenticate a caller's facts.

The simulator exercises matching and unaffected actions, selected actions individually, exact duration boundaries, missing/invalid clock facts, scope mismatches, unknown effects, generic alternate routes, overlapping denial and human-only administration. Results pin the entire wording/structure plus semantics/suite versions and always say execution is disabled. Passing simulations are not live browser/native containment evidence.

## Vault and model review

`CardinalDraftStore` stores each draft and its review/test results in the existing encrypted, versioned protected Vault records. There is no settings copy. Incomplete drafts can be retained but cannot pass validation. Every edit clears review/test results. Writes recheck the live super-admin role, exact Vault reference, lock state, authority epoch and recovery reconciliation. A late model reply cannot attach after an edit, lock/unlock or role loss. Audit failure rolls the version/result back. Ciphertext digests, not low-entropy wording hashes, appear in the ordinary index/audit.

`reviewCardinalMeaning` uses a supplied connected registry provider without tools, task context or a vendor JSON-mode prerequisite. The caller must resolve the currently selected provider with the existing credential, local-only and external-transmission checks. The reviewer receives only the explicit preview: wording, generated structured meaning and rule guidance. Scope IDs are replaced with placeholders. The wording itself cannot reliably be scrubbed of arbitrary secrets; the protected UI must show and authorize the exact preview before sending it. The draft store verifies that preview's digest. No other Vault records or conversation history are sent.

The model returns clarity, explanation, concerns and suggested wording. Extra approval fields, malformed responses and tool requests are rejected. Provider errors are redacted and recorded as unavailable review, without invented advice. Model concern/clarity remains separate from deterministic results: neither a favorable nor an unfavorable opinion changes a rule or activates it. Draft text is never executed as a model instruction or silently replaced with suggestions.

## Remaining P3 acceptance

- Protected editor/preview and Test Rule HTTP integration, with current provider-selection fencing and safe result rendering.
- Install the real authenticated human-only control boundary and expose the tested backend lifecycle through the protected UI. Activation currently requires an additional server-owned protected-human verifier that has no production implementation; no public activation/mutation route is exposed.
- Integrate restrictive active-policy evaluation with final dispatch, implement enforcement revalidation and verified recovery reconciliation. Restored rules are inspectable; they do not reactivate dispatch authority.
- P4/P5 device/desktop containment that prevents automation from operating protected administration, including alternative routes. A password field alone is not proof of human presence.
- Broader measurable restrictions only as their verifiable adapters become available, plus live executor/bypass acceptance in dependent phases.

The semantics matrix exercises all supported action names against both restrictions and both missing-fact modes. Core/LLM/API/worker TypeScript builds, whitespace checks and the public-source secret scan passed (1,085 files). One initial assertion compared JSON property order instead of content and was corrected; no production parsing change was needed for it. All fixtures are synthetic; no live model was called and no rule was activated.

## Exact-command administrator reauthentication checkpoint

The auth package now issues a two-minute, one-use verification for an exact protected command after checking the current super-admin account, live session, fresh password and enabled MFA. It is not the existing reusable step-up unlock. Migration 0076 stores only salted/keyed verification hashes, session identity, authority epoch, expiry and consumption metadata; it contains no rule, command body or credential value. The ephemeral proof stays inside a closure and serializes as a redaction marker. Restart discards it. Account-scoped attempt limits apply across sessions.

The draft store derives the command binding from the actual saved draft or test request, including the exact Vault reference, preview and model identity. A server-owned access callback checks and consumes the proof inside the same transaction as the protected record. Session revocation, password/authenticator changes, role loss, Vault lock/unlock/recovery, expiry and changed command/model reject it. Reads before a model review do not consume it; the final result write does. A failed record/audit write rolls consumption back, permitting only the exact authorized retry. MFA recovery-code consumption and verification issuance are also one transaction.

This verifies fresh account credentials, **not human presence**. It cannot by itself satisfy the protected-client boundary, and no activation endpoint or human-only claim is introduced. P4/P5 must keep automation out of the protected control surface and supply that additional authority before permanent activation can be exposed.

Executed: 72 tests passed across protected administrator verification, MFA, drafts, protected records, rule semantics and fresh-database migration suites. Core/auth/LLM/API/worker type builds and the public-source secret scan passed (1,088 files). Added cases cover exact-request/model substitution, delayed-review session revocation, one concurrent winner, expiry, account/security changes, audit/write rollback, required MFA, one-use recovery codes and account-wide throttling. No real account, factor or installed-server data was used.

## Permanent-policy storage and restrictive evaluation checkpoint

Migration 0077 adds a protected policy record kind. The existing generic record writer refuses it. The guarded lifecycle uses one fixed Vault record identity and retains encrypted versions for activation, replacement and retirement. A draft edit preserves the previous active definition until the new draft is tested and confirmed. Retiring the last rule leaves an explicit empty policy snapshot; deleting/missing policy storage never means permission.

Activation checks the exact current draft and policy references in one transaction, recomputes the deterministic report, verifies the pinned semantics/test versions and verifies the currently selected model revision. Model advice must exist, but its favorable/unfavorable opinion cannot decide activation. Both fresh administrator verification and a separate protected-human control verifier must pass for activation or retirement. The human verifier is a trusted server integration, not a client-supplied boolean/function. There is no production verifier or activation HTTP route in this checkpoint. Tests inject a clearly identified fixture and do not prove native human presence or protected-screen containment.

Receipt consumption, the new policy snapshot, epoch and audit share a transaction. A concurrent edit, reused confirmation, model replacement, stale tab or failed persistence cannot partially activate a policy. The protected record size/count bounds also fail without replacing the previous policy. Inspection reports recovery reconciliation and enforcement freshness; old enforcement/test evidence cannot become current just because another rule was added.

The internal engine reader consults the current Vault and active user, checks an optional expected policy reference and returns only a restrictive verdict and rule references. It does not disclose wording/reviews to ordinary execution. Missing/corrupt policy, unavailable Vault, restored authority and outdated enforcement pause; an unaffected action returns `no_restriction`, never an execution grant. Rules continue to constrain ordinary users if the administrator who created them is later disabled. P4 must supply authenticated complete effect facts, device consent and ordinary grants, then bind the result to final dispatch; this reader is not a lease and cannot recall a completed external action.

Executed: 46 tests passed across policy lifecycle, drafts, protected records, administrator verification and fresh-database migration suites. After tightening inspection/enforcement freshness consistency, the 11 policy tests passed again. Core/auth/LLM/API/worker type builds and the source secret scan passed (1,091 files). The first lifecycle run found an incomplete synthetic model fixture (missing the database-required probe evidence); the fixture was corrected without relaxing the constraint. Coverage includes unchanged active rules during editing, exact replacement/retirement, absent human verifier, stale/competing confirmation, model replacement, invalid test evidence, rollback/retry, ordinary-user redaction, disabled authors, locked/corrupt/missing Vault authority, restore reconciliation and default-model subscription metadata. No real model, confirmation device or automation executor was used.

## Vault-derived protected review checkpoint

The policy store now provides `prepareActivation` and `prepareRetirement`. Both read exact current Vault references and reuse the mutation's validation. Preparing a review does not change the authority epoch, consume credentials, activate a rule or require a model call. Activation preparation rechecks the deterministic test report and selected review-model revision; stale, untested or recovery-blocked definitions cannot produce an actionable review. Retirement also requires current enforcement semantics before displaying what would be removed.

The full wording comes from the saved definition. Enforcement meaning is generated from its structured fields. Replacement displays the previous wording/enforcement alongside the new meaning; retirement identifies the exact restriction being removed. The saved model clarity assessment, summary, every concern and every suggestion remain separately labeled as advice. Model `needs_clarification` still does not approve or veto the administrator's decision. Nothing is silently truncated. The shared protected-presentation contract now permits 64,000 meaning characters and twenty advisory entries of 2,600 characters, enough for old/new maximum identity scopes and the existing complete model-review fields; unsupported display-control characters or content beyond the bounds are refused.

At mutation, the store regenerates the expected presentation from the same locked Vault state and passes it to the protected-human verifier. The server challenge verifier compares that entire expected presentation with the signed one. A valid signature over the right command but misleading wording/meaning/advice is rejected, with no policy change or consumed account proof. Thus a renderer/model paraphrase cannot replace the generated enforcement statement during the final write. Real enrollment, native presence, key projection and HTTP/editor assembly remain open; the protected server verifier and native window checkpoints are described in [P4 evidence](P4_PERMISSIONS.md).

Validation: 63 tests passed across Cardinal policy, server confirmation, host confirmation and protocol suites; another 48 passed across automation policy/reservations, Vault records and administrator verification. All 19 desktop tests and the full root TypeScript build passed. Added tests cover read-only preparation, selected-model changes, old/new and retirement display, complete maximum identity scopes, unsafe text refusal, and actual fixture signatures over misleading versus exact generated meaning. No live rule or installed data was changed.
