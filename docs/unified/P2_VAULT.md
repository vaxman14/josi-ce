# P2 Vault authority implementation evidence

Date: 19 October 2026. In progress. P0 and P1 checkpoints are on the authorized GitHub branch (`1f40c4f`, `48b5215`). This checkpoint supplies protected storage, not active rules or an automation executor.

## Implemented and checked

Migration 0066 adds versioned protected records and an authority epoch to the existing Master Vault. Rule drafts, meaning reviews, and deterministic-test records are encrypted under the vault’s existing independent master key. Only metadata and ciphertext digests are indexed; there is no plaintext rule preview or second key store. Generic credential deletion cannot affect these records. Writes check the active super-admin row, compare the exact prior reference, preserve old versions, and commit the new version, epoch, and redacted audit together.

Reads re-open the current vault rather than treating an in-memory copy as authority. Ciphertext authentication binds record identity, kind, schema/version, author, prior digest, and epoch. Exact-reference reads reject stale versions/epochs. Lock/unlock changes invalidate references. Recovery retains the existing vault key and both credential and record access, invalidates prior references/UI unlocks, and requires authority reconciliation before further protected writes or exact-reference checks. There is deliberately no shortcut to clear this flag; P3’s verified revalidation flow must supply it before release. Recovery display remains available for inspection.

Credential references now verify the referenced item ID as well as owner/service/slot. A reference to a deleted item cannot silently resolve a newly created credential in the same slot.

Executed checks: 13 core vault/record tests passed; 71 API vault/LLM and registry regression tests passed; `tsc -b packages/core apps/api` passed. Tests cover concurrent edits, live-role changes, master lock, failed audit rollback, ciphertext transplant, uninitialized vault, unsupported kinds, oversized values, missing transactions, replacement-install-key recovery, and credential-reference substitution/deletion. All test databases and keys are synthetic.

## Remaining P2 work

The [credential inventory](P2_CREDENTIAL_INVENTORY.md) tracks all consumers, including authentication factors, temporary login verifiers, installer service material and CLI login projections.

- Migrate all identified canonical credential consumers and eliminate legacy direct-ciphertext writes once their compatibility migrations are verified. Current ordinary credential helpers still retain their preexisting legacy behavior; this checkpoint does not claim vault-only migration is finished.
- Complete remaining workflow/backup/CLI/bootstrap consumers and desktop session projections. Implemented consumer checkpoints are recorded below. Preserve owner/device fencing, revocation and backup/recovery throughout the full upgrade migration.
- Implement browser encrypted-workspace authority and short-lived execution projections in the dependent runtime phases.
- Add authenticated dispatch freshness and remote-device reconciliation with P3/P4. A reference is a consistency token, not a bearer permission. The record store is an internal API, with no public HTTP/LLM mutation route or activation operation.
- A complete database rollback cannot be detected by a counter stored only in that same database. Paired devices must retain their last acknowledged authority generation and refuse rollback/re-enrollment shortcuts; restore workflows must reconcile before execution. Do not claim this unimplemented integration is proved by storage tests.

The installation key and recovery material remain the bootstrap root of trust. This implementation neither replaces them nor silently imports live user secrets. Tests do not alter an installed server or current user vault.

## Mobile push and recoverable credential references

Push registrations now store the token only in the owning user's Vault box. Registration, account switches, legacy-token import, reference replacement and canonical-slot removal share the existing global registration fence and database transaction. Provider receipts retain the sent-token fingerprint check before revoking or deleting a current credential. Explicit device revocation remains available while locked. Master/box locks defer sending without consuming delivery attempts; unlocking can resume the queued notification. An already-started bounded provider request cannot be recalled by a later lock.

Credential references now use a versioned, authenticated envelope under the existing recoverable Vault key, including item identity and owner/service/slot context. A replacement installation key can resolve migrated references after recovery. Telegram, Slack/WhatsApp and mobile readers upgrade older install-key references as well as legacy secret payloads. The LLM reader recognizes the new envelope. Ordinary consumers that have not yet migrated their older references still require the original installation key; the remainder of P2 must remove that dependency before release. No fallback to a different item in the same slot is allowed.

## Account tokens and Nextcloud reconnects

Connection creation/reconnect now requires the Vault and commits credentials, capabilities and audit together. A missing targeted connection cannot be silently recreated. Failed refresh-token preservation stops reconnect rather than dropping the existing token. Legacy payloads and correctly bound older references migrate during credential access. Current owner/provider/account/destination/scopes and active status are checked before use; deleted/revoked or changed-destination snapshots are denied.

Refreshes share an owner/provider fence with reconnect/removal and re-read current tokens, so competing requests do not renew the same expired token twice. The advisory fence is acquired before Vault state, then the connection row, so queued refreshes do not hold a shared Vault lock while waiting behind a provider. Each provider renewal has a maximum configured 20-second request timeout; an in-flight renewal may delay a later Vault lock until its transaction ends. This is not a total lock-latency guarantee or P4's business-action dispatch authority. Failed database commits roll back canonical/local changes; they cannot undo a provider-side token rotation, which can require reconnecting.

Nextcloud reconnect reuses the existing connection ID and Vault slot. Previously it could upsert the old database row while issuing a credential reference for a new UUID, leaving an unusable reference. The new path prevents that mismatch and orphan slot on new reconnects. Old inconsistent references remain fail-closed and must be identified in the full upgrade flow for explicit repair/reconnect; they are not silently treated as permission to read another slot. Credential/destination matching is enforced on reads. The provider-disconnect reader now applies Vault/box checks to legacy credentials after local withdrawal; local deletion remains available while locked.

Executed: the broader affected run covered 18 suites; two existing automatic-calendar fixtures lacked the new Vault prerequisite. After correcting those fixtures, the final focused run passed 112 tests; aggregate distinct coverage is 368 passing tests. Coverage includes replacement-key recovery, old-reference/context checks, repeated Nextcloud reconnects, master/box lock denial, competing refreshes, lost refresh-token prevention, import/refresh/reconnect/audit rollback, missing-target denial, provider-revocation access and existing agent/worker approval behavior. Connector/agent/API/worker type builds and source checks passed. Concurrency tests use PGlite's transaction adapter; separate multi-process PostgreSQL acceptance remains a release check.

## Account authenticators and locked-Vault recovery

TOTP setup now stores a recoverable Vault reference in the account row. Setup, enablement, legacy/reference migration, disablement and their canonical changes commit transactionally. An enabled authenticator cannot be silently replaced by restarting setup or enablement. Generic Vault item creation/edit/deletion cannot mutate the reserved authenticator service; its lifecycle belongs to Security settings. Apple linking and parental authority share the same Vault-aware factor reader and retain their first-factor checks.

Ordinary MFA login atomically consumes its challenge and optional recovery code, inserts the session and records its audit. Failed session/audit insertion rolls the entire operation back. Master/box locks leave the pending challenge and its attempt allowance untouched. Recovery codes remain one-use, one-way verification hashes and work without opening the Vault; missing installation keys or missing authenticator secrets no longer bypass enabled MFA. Invalid factors retain the five-attempt bound. Disabling MFA still requires the existing password and removes the canonical slot and pending MFA challenges even while locked.

Native MFA completion now follows the existing no-Origin native authentication boundary and returns its bearer session, with the same persistence choice as password login. Browser requests, including those claiming the native marker, still require CSRF protection. Existing Apple/parental workflows consume recovery factors before their later workflow commits; a later failure can require a fresh recovery code. This checkpoint does not claim those broader workflows are one atomic transaction or that TOTP codes are globally replay-tracked.

Executed: 111 tests passed across eight auth, Vault, native Google/Apple and parental suites. Added coverage includes replacement-key recovery, legacy import, cross-account substitution, master/box lock and missing-key recovery, no-second-factor bypass, competing challenge consumption, failed session/audit/setup rollback, expired/disabled accounts, active-factor overwrite prevention, native persistence and browser CSRF enforcement. Auth/API/worker type builds, whitespace checks and the source secret scan passed (1,060 files). All keys/accounts are synthetic; no installed-server credentials were changed.


## Model-provider credentials and probe ownership

Migration 0072 binds model credentials to a stable Vault owner. Older reference ownership is recovered from its authenticated item pointer, including after administrator succession; it is never inferred from arbitrary same-named Vault items. Previously unbound direct ciphertext imports into the administrator's box. Setup and admin saves share one transaction for credentials, configuration, probe invalidation and audit. Required fields are validated against the actual merged credentials. Blank fields retain existing secrets only within the same provider; changing providers requires new credentials. Switching a migrated slot to a keyless provider or removing it deletes its canonical credential while locked. An unbound older secret must first be opened to establish its owner.

Registry preparation rechecks the persisted provider, model, destination, settings and revision before resolving a key. It rejects changed/deleted selections, requires an unlocked Vault, and atomically migrates older ciphertext/references. Capability probes carry the exact prepared revision, including a migration performed during preparation. Both admin and setup activation compare that revision; a passing old probe cannot activate a concurrent replacement. Setup verification and activation now commit together. Credentials remain absent from public configuration and audit payloads.

This is credential preparation, not P4's final dispatch authority: an already prepared provider can complete its bounded requests after a subsequent lock. Subscription CLI login directories are still listed separately as unfinished migration work. No provider was contacted with live credentials during these checks.

Executed: the final affected run passed 152 tests across eight suites. Earlier expanded runs also passed the agent, personalized-turn, assistant, claim-guard, Telegram, worker and full setup regressions; old fixtures were updated to initialize the Vault. Added checks cover historical/current ownership, replacement-key recovery, partial credential updates, locks, stale/cross-slot references, configuration/audit rollback, uninitialized denial and concurrent setup-probe replacement. LLM/agent/API/worker type builds, whitespace and the source secret scan passed (1,063 files). Migration/rotation concurrency is exercised through the existing PGlite adapter; multi-process PostgreSQL acceptance remains a release check.


## SMTP profiles and shared credentials

Migration 0073 binds SMTP profiles to stable Vault ownership. System and communications settings, their canonical credentials, verification invalidation and audit commit together. Invalid communications input or a failed second write cannot leave only the system profile changed. Older ciphertext and references migrate under Vault/box checks. Authenticated pointers recover historical ownership after an administrator change; raw legacy ciphertext imports into the administrator's box. Recovery with a replacement installation key preserves migrated mail credentials.

A communications profile that borrows the system server retains its own sender identity and stores no duplicate password. Switching from independent to shared SMTP removes the former communications credential. Blank password updates retain a password only for the same server/port/security/account; changing that identity requires a new password or explicit clearing. Gmail app-password spacing is normalized for either independent profile. Removal clears migrated canonical slots even while locked; removing the system profile also removes a dependent borrowed profile, while preserving independent communications settings.

Setup records SMTP verification only for the exact profile revision used by the test. A concurrent replacement cannot inherit success from a message sent through the previous settings. The test still reports server acceptance separately from actual delivery. Mail APIs report a Vault lock before constructing their send transport. Credential resolution is not a guarantee that an already prepared SMTP request can be recalled after a later lock; final dispatch controls remain P4 work.

Executed: 253 tests passed across ten mail, setup, authentication and fresh-database suites. Coverage includes shared sender identity, historical ownership, replacement-key recovery, legacy import, cross-profile substitution, master/box locks, deletion, explicit clearing, changed-destination password refusal, invalid second-profile rollback, failed audit/write rollback, Gmail normalization, API lock/retry and stale SMTP verification. ## Per-user developer connections

Developer-service tokens now use strict owner/service-bound Vault writes and transactional legacy/reference migration. Save, rotation, removal and audit share a per-service transaction fence with administrator permission changes. The existing connection owner remains canonical; no administrator-owner reassignment is introduced. Disconnect removes the canonical item even while locked or no longer permitted.

The HTTP connection test checks Vault and permission before contacting the provider, then rechecks before committing a verified token. Saved-token checks now honor revoked permission as resource tools already must. API and agent readers share the same active-account, policy, Vault/box and connection-status checks. Explicit rechecking may test a connection needing reconnection; ordinary resource use cannot. Replies update health only if the exact credential reference and permission remain current, so an old failure cannot overwrite a replacement or revive a deleted connection. A Vault refusal performs no provider call and does not poison health. Transient resource-discovery failures preserve the existing active status.

## Workflow provider and callback credentials

Workflow provider tokens and callback verifiers now commit as one recoverable Vault pair with their stable integration identity and audit. Reconnecting rotates the provider token without silently changing the verifier configured at the provider. Disconnect clears both references and canonical items even while locked. Legacy pairs migrate transactionally; a failed second write or reference update leaves neither a partial pair nor an orphan integration.

Discovery checks the Vault before contacting a provider, publishes its catalog atomically, and discards late results after reconnect/removal. Vault refusal does not mark a healthy connection broken. Run proposals check the current exposed workflow and Vault; a known lock leaves approval pending. Competing decisions still have one winner, and a second credential check after the claim stops dispatch if authority became unavailable. Approvals now bind the callback reference and private-network setting as well as the original provider, destination, credential and workflow schema. Older pending approvals with the former boundary require a new proposal; they are not silently upgraded into permission.

## Backup destination and archive-encryption credentials

Migration 0074 binds the destination credential and archive key independently to their actual Vault owners: older administrator edits could have placed them in different boxes. Authenticated historical pointers recover those owners; raw legacy ciphertext uses the existing administrator fallback. Paired writes/imports, configuration revision, verification invalidation and audit are transactional. A prepared edit cannot overwrite another completed edit. Master/box locks and replaced settings prevent credential preparation and offsite dispatch. Connection-test results apply only to the revision actually tested.

Partial credential updates preserve missing fields only for the same storage endpoint; an account change requires its corresponding secret. Changing the NAS host/share cannot silently reuse the old credential or downgrade to guest access without explicit clearing. Embedded URL credentials/query parameters are rejected. Disabling encryption retains the archive key for older encrypted copies, and re-enabling does not silently rotate it. A bound destination can be removed while locked. Separately held archive-key material can open the outer encrypted envelope without accessing the Vault; this avoids a circular decryption dependency but is not an end-to-end bare-machine restore claim.

NAS configuration commits before applying a runtime mount, because the legacy Docker controller may restart CE. Untested settings do not authorize backup upload. Controller receipts name the exact configuration revision; stale/unconfirmed mounts cannot pass the API's preparation check. Browsing uses a disposable volume and credential file, leaving the active mount untouched. The helper always replaces the credential projection from the supplied canonical value instead of preserving an independent old file. Failed projection is reported separately from saved settings, without exposing the helper's error. The web form retains the selected NAS subfolder on edit and displays application failures.

Executed: aggregate affected coverage is 166 passing JavaScript tests across six backup/API/installer/fresh-database suites, with the final changed HTTP suite passing 28 tests. Five Python helper tests also passed. Added checks cover separate historical owners, replacement-key recovery, offline outer-envelope decryption, partial edits, retention across encryption toggles, context substitution, lock/health behavior, migration/write/audit rollback, competing edits, stale tests, real HTTP encrypted-upload preparation and size verification, lock/reconfiguration during local archive creation, isolated browsing and mount receipts. Ops/API/worker/web type builds, whitespace and the source secret scan passed (1,074 files). All storage, archives, credentials and helper commands are synthetic; no live NAS, Docker mount or cloud bucket was changed.

Remaining gates: outer-envelope import and complete restore/reconciliation; reliable offline archive-key delivery/acknowledgment across a controller restart; historical-key retention/explicit removal semantics; durable retry of failed mount cleanup; and revocable runtime projections with current authority at actual filesystem dispatch. The legacy helper's credential file/mount still needs that P4/P5 lifecycle, including shutdown/lock and restart behavior. A receipt comparison is not a lease or an atomic filesystem-operation guard, and preparation cannot recall an in-flight upload. These are tracked work, not secret-store exceptions or a completed P2 claim.
